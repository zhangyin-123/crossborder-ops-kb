## 1. 系统架构与角色分工

```
GitHub 共享知识库 → Muse 制定运营方案 → Codex 独立审核 → 用户批准
→ 紫鸟 Agent 执行 → 结果回传 → Muse 复盘优化 → 写回知识库（草稿）
```

| 角色 | 职责 | 权限边界 |
|---|---|---|
| Muse（首席运营策略） | 制定选品、定价、商品内容及日常运营方案；分析紫鸟回传数据；持续优化标准与策略 | 只输出方案、策略、任务安排。禁止直接登录、修改店铺后台；禁止碰账号密码；禁止动钱 |
| 文字助手 | 英文标题、五点描述、搜索关键词、主图提示词、本土化文案、标题对比测试、短视频脚本、竞品公开文案拆解 | 素材类任务可由 Muse 直接下发；产出返回 Muse 汇总 |
| Codex（独立审核） | 独立审核每个运营方案：来源、数据、定价验算、合规、风险 | 只审不改、不执行。审核意见写回方案文档；未通过的方案不得发给紫鸟 |
| 紫鸟 Agent（执行，含 WakeBody） | 在紫鸟隔离浏览器内执行商品修改、改标题、改图、调价、上新、活动报名等后台操作 | 唯一允许操作店铺后台的工具。只存待发布草稿，等用户手动点发布；执行时遵守风控规则 |
| 用户 | 最终批准人；手动发布；提供店铺数据、成本、账号与窗口位置 | 所有后台操作类任务须用户确认后才下发；所有花钱的动作须用户点头 |

协同规则：素材类任务 Muse 可直接下发文字助手；后台操作类任务先发完整方案和指令模板给用户，确认同意后 Muse 再下发给紫鸟 Agent。下发给紫鸟 Agent 的任务，必须把完整任务文本直接粘贴发送到其当前聊天对话窗口，以消息形式发出，不能走后台静默调用；紫鸟 Agent 在该窗口回复收到、说明开始执行并同步进度，成功或失败全部在窗口输出文字结果、报错截图提示。

### 2.2 检索方式

- 命令行：`python3 scripts/search_kb.py "关键词" [--status approved|draft] [--json]`
- MCP 服务：`crossborder-ops-kb`（`scripts/mcp_server.py`，stdio），工具 `search_knowledge(query, status, limit)` 与 `read_knowledge(id, status)`，均为只读。Codex 与 Muse Code 共用同一本地 MCP 服务。
- 检索顺序（按仓库 AGENTS.md）：先看 `knowledge/INDEX.md` → 用 `search_kb.py` 查已批准文档 → 读正文。只引用已批准资料；草稿、过期、已撤销资料不得作为确定性结论。

### 2.3 关键机制（容易踩坑的两点）

- **已批准检索读的是 origin/main 的不可变快照**（`kb_core.py: published_files`），不是工作目录文件。main 上目前 0 张卡片，所以 approved 检索恒为空。
- **草稿检索读的是本地工作目录磁盘文件**。本地当前检出的是 main（0 张卡片），所以 draft 检索也返回空。4 张草稿只存在于 `origin/review/intake`，要查草稿须检出该分支或用 worktree，例如：`git worktree add ../crossborder-ops-kb-intake origin/review/intake`，再在该目录运行检索。

### 2.4 卡片结构

- Front-matter 11 个字段，缺一不可：`id, title, platform, market, topic, status, source, checked, effective, expires, tags`
- 路径规则：`knowledge/<platform>/<topic>/<id>.md`，`id/platform/topic` 须为小写 slug
- 状态机：`draft`（默认）→ 人工审核 → `approved`；过期（`expires` 早于当天）按 `expired` 处理；`withdrawn` 为撤销
- 已批准卡片额外要求：`market、source、checked` 不得为空；日期须为 `YYYY-MM-DD`
- 校验：修改后运行 `python3 scripts/validate_kb.py`（只校验结构，不能证明内容真实）

## 5. 商品内容标准

- 标题、五点、关键词、主图提示词由文字助手产出，Muse 汇总后发用户审核；审核通过后紫鸟 Agent 再完善信息、保存为待发布草稿，不自动发布，等用户手动发布。

- 带货视频：材质必须与产品原图一致，AI 重画走样不可接受；不接受轮播图式视频；雷锋帽视频须展示全部 4 色、男女模特都要、有人声口播讲清保暖卖点、男女混合播音；毛边须与实物一致（实物毛本来就密厚）；发布须开 AI 标注。
- 素材标准：英文本土化标题、搜索关键词、五点描述，适配买家习惯，主图清晰有吸引力。

### 8.2 提交与审核步骤

1. Muse 按第 7 节模板写好方案（Markdown），存入 workspace，并同步一份到仓库 `review/intake` 分支指定位置（走 inbox/ 流程，不直接改 main）。
2. 在 Mac 端由用户或 Codex 定时任务触发：`codex exec -s read-only -C <仓库路径>`，提示词写明：按仓库 AGENTS.md 与本规范逐项审核（来源、地区、适用平台、失效日期、版权、数据敏感性、定价验算、合规、风险），输出通过 / 有条件通过（列出须改项）/ 不通过（列出理由）。
3. 审核意见写回方案文档第 8 节“审核记录”。有条件通过的，Muse 按意见修改后重新提交审核；不通过的，停在原地，不得发给紫鸟。
4. 审核通过后，方案再交用户批准；用户批准后，Muse 按第 1 节协同规则下发给紫鸟 Agent。
5. 紧急情况下用户可书面豁免某次 Codex 审核，豁免记录在方案文档第 8 节，事后补审。

### 8.3 审核要点清单

来源是否可追溯、适用地区与卖家类型是否对得上、政策日期与失效日期是否在有效期内、版权与数据敏感性、定价是否用计算器主口径逐项验算、类目与合规是否符合三档分级、执行步骤是否可在紫鸟隔离浏览器内完成、风险点是否列全、是否包含客户资料或密码。
